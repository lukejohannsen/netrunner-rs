# Phase 4 — Network Resilience & Server Infrastructure

Area roadmap; the index is `ROADMAP.md`. Addresses: "Phase 4 §1"–"§6". The server sends **full masked `ClientView` snapshots** after every action, not deltas — the current design, not an oversight (§4).

## 1. Event Stream to Clients — DONE
`ServerMessage::ActionLog` carries one entry per action (since Phase 1.5). **Masked per viewer** (`fix/masked-action-log`): the raw entry had gone to both seats, naming unrezzed installs and access picks. `rules::masking::mask_action_for_player -> PublicAction { Visible | Concealed(ConcealedAction) }` — the six card-naming shapes keep their structure, because "the Corp installed into Remote 0" is information the Runner must have; `mask_event_for_player` drops an event whose information *is* a concealed identity and strikes the card out where it can, reading **conservatively from the post-action state**. `netrunner_session::PublicHistoryEntry` is reached only through `Session::last_entry_for(side)` — valid right after the action, no batch form, because masking an old entry against a later state reveals cards. The TUI pumps `step` one action at a time. Gate: `no_client_view_or_log_entry_ever_names_a_card_it_conceals`, widened to the opponent's hidden zones. **Closed 5 September 2026** (`feat/narrated-action-log`): `CardInstalled`, `CardAdvanced` and `IceSwapped` carry an `InstallId` and an `Option<CardId>`, so masking strikes the identity in place — the third, fourth and fifth fields that can be, after `TraceInitiated` and `PendingCardSelectionOffered` — instead of dropping the event. The handle is public (`PublicInstalledCard::install_id`), and for advancement so is the count, so the dropped event had been telling a viewer *less than their own board already showed them*. A swap is the case that needed it most: it comes from a card's text (Tāo Salonga, Brân 1.0) and no `PlayerAction` names it, so the event was the Runner's only possible record and there was none. `netrunner_cli` now narrates: `app::narrate_event` renders a line per event that says something the action line cannot, exhaustive over all 100 variants with 97 grouped as not-narrated, resolving every handle through the shared `app::install_label` against the viewer's own `ClientView` rather than trusting the event to name anything. A Runner reads "advanced the unrezzed card at Remote(0), now at 3 advancement tokens" where the log was previously silent. Gates: the fog sweep gained `assert_every_install_event_keeps_its_handle` (a real handle, not `InstallId::PLACEHOLDER` — the scan for leaked names cannot tell an event that says nothing from one that says which), and an `app.rs` test plays six real matches and checks each rendered line against what that seat concealed *at the moment it was written*. **Extended and closed 5 September 2026** (`feat/narrate-consequences`). The note above was wrong about half of what it deferred. `CardMoved` and `CardDerezzed` took handles on the same argument as the first three — a move keeps the card's install id and both servers are public, a derez is a rez state flipping on a public handle — and now strike rather than drop; they fire **42 and 19 times in 132 random-vs-random games**, so this was not a corner. **`CountersAdded`/`CountersRemoved` must not, and that is the durable finding**: `PublicInstalledCard::counters` is `None` on a face-down Corp card for its own stated reason, "whose counters would otherwise leak what it is (a *Nico Campaign* draining credits is recognisable long before it is rezzed)", so "the counters on install #7 changed" publishes exactly what the view withholds. They stay dropped, the reason is on the variants and on the masking arm, and `counters_on_a_facedown_install_stay_dropped_rather_than_struck` fails if anyone completes the pattern. Counters are the most common of the five by far (1,803 added, 1,118 removed in the same 132 games), which is why the leak would have mattered.

Narration widened from 3 events to 31 in the same pass, on a criterion stated once: narrate what no `PlayerAction` implies and a player would want logged — damage, tags, a trigger firing, a subroutine resolving, an agenda's point value, how a run ended, whether a trace landed — and stay silent on bookkeeping. Duplicates are suppressed in one `action_implies` helper (rez, remove-tag, click-break, install, jack-out) rather than per arm. **Measured over six matches: 73 narrated lines before, 519 after**, against 2,172 actions; over the 132-game report the narrated set covers 13,688 event occurrences. Narration needs no leak analysis of its own — it runs on an already-masked entry — but the UI is where a rendering mistake would show, so the end-to-end test became `no_rendered_log_line_names_a_card_the_seat_conceals`: **every** rendered line, checked against the board as it stood when that line was written, minus titles the view accounts for elsewhere (two copies of one ice, one rezzed, make the name printable) and minus what the seat's own action names (it accessed the card). The sweep's `assert_every_install_event_keeps_its_handle` now covers all five events.

## 2. Reconnection & Session Recovery — DONE
`feat/reconnect-handshake`: a per-seat `session_token` (v4 `Uuid`) in `MatchJoined`; `ClientMessage::Resume` answered with `MatchJoined` and a fresh `StateUpdate`, or `ResumeRejected`. The seat outlives its channel pair (`ChannelSeat.detached`, `ReattachHandle`; `await_seat` is a `select!` over the seat's rx, the reattach channel and the deadline); **newest connection wins**. **The grace clock (`DEFAULT_RECONNECT_GRACE` 30s) starts when the seat is needed**, resets on reattach, and expiry reports `GameEndReason::Disconnected` — a transport outcome, never from `classify_end_reason`. Tokens live in `serve` (`SeatTicket`), registered in `start_match`. The client's `Reconnector` makes one bounded attempt per render tick, 60s total — longer than the grace so a forfeited seat learns it from `ResumeRejected`. Dropped `ActionLog` entries are not replayed. Fixed in passing: a ping frame ended the stream.

## 3. Multi-Match Daemon & Matchmaking — DONE
- **Registry, lobby queue, rooms, cap, per-match seed** (`feat/match-registry`): one `Registry` under one `std` mutex — the operations that matter are compound (a pairing must sweep the lobby, check the cap, claim an index and register two tickets as one step). The lobby is a queue and **a waiter's token is the seat's token** (`Queued { session_token, position }`); ghosts are swept on every pairing and `ListMatches`; `ListMatches → MatchList` of `MatchSummary`; `--max-matches` refuses with `ConnectRejected` before queueing; `--seed` fixed (match `n` plays `seed + n`). `--room` in the CLI. Open: resuming a lobby place from the CLI; a graceful shutdown.
- **Turn timers** (`feat/turn-timers`): `--turn-timeout-secs`, **per decision**, cleared only when an action *applies* (a rejected action does not restart it), not reset by a reattach, and it **forfeits, never auto-plays** (`GameEndReason::TimedOut`). `DecisionClock { side, remaining }` once per decision; nothing is sent when the clock is off.
- **Spectators** (`feat/spectators`): `Spectate { match_id }` → `Spectating` plus every update, masked as `Viewer::Spectator` — **the intersection of what the two players see**. Every gate reads `viewer.is(owner)`, so there is no third code path; every masking entry point takes `impl Into<Viewer>`; `ClientView.side` became `viewer`. The fog gate checks the spectator against the union of both concealed sets. `SeatControl::{Reattach, AddSpectator}` on one control channel; spectators are drained sinks holding no token. CLI `matches`, `--spectate`. Open: spectator counts and caps; a delayed omniscient stream.
- **The daemon deals the published pool** (`feat/serve-plays-the-sample-pool`): every hosted match had been on the blank-padded Kate-vs-HB fixture (24 of 45 Corp cards did nothing), so every rating ever written was on that board. `sample_decks_for_seed(seed) = matchups()[seed % len]`; `--corp-deck`/`--runner-deck` pin a side at `bind`. Deleting the fixture deleted the `netrunner_cli::decks` mirror of it. Decklist ids are on the wire (`MatchJoined`, `MatchSummary`, `#[serde(default)]`). Open: `netrunner_single_player/tests/common/mod.rs` holds the last filler near-copy; the TUI header does not show the matchup.
- **A player brings their own deck** (`feat/online-from-the-menu`, Phase 6 §3, 13 September 2026): `Connect { deck: Option<Box<DeckFile>> }`, `serde(default)` and skipped when `None`, so an older client still connects and is dealt one. **The deck is the seat**: its side overrides a preference, a contradicting `preferred_side` is refused, and it is validated against the daemon's `--format` at the door (`check_brought_deck`, the same `DeckFile::validate` a pinned deck gets) — refused with `ConnectRejected` before it reaches the lobby or a bot. It replaces the deal for its side in `start_match`, pin or rotation; the operator's pin is the default for a seat nobody brought a deck to. **Pairing respects it**: `compatible` skips a waiter whose deck is for the same side, so two Corp decks both wait for a Runner rather than one being seated as the Runner (`two_decks_for_the_same_side_never_pair`). A daemon older than this ignores the field and deals, which the client detects by comparing `MatchJoined`'s deck id and says on the header. Also: the CLI sends the player's own name instead of `"CLI Player"`, `--deck` brings one on the flag path, and the client's writer closes the socket with a `Close` frame when its sender goes, so an abandoned lobby wait leaves the lobby instead of being paired as a ghost.

## 5. A rating is a server's to keep: identity is a key, a game leaves a signed receipt — OPEN, design only (20 September 2026)

`docs/server-tracked-rating`. **No code; the reasoning is `docs/identity-and-rating.md` and this entry is its index.** It follows `fix/local-play-is-casual` (Phase 3 §2, same day), which took the rating *out* of the client: a rating is a claim to someone else, so it means something only between people and only when somebody other than the rated player keeps it. What is left to decide is how a server keeps one, and the hole in what it does today.

**The daemon already rates human against human, under whatever name the client typed.** `Track::HumanVsHuman` and `Shared::rate` work and survive a restart (`tests/lobby.rs`), but the participant id is `Connect.player_name`, unverified (`PendingHuman::seated`). Anyone can be anyone. And the evidence is thrown away: `MatchRecordHeader` + the JSON-Lines `MatchHistory` replay bit-identically, and `MatchSession::run_with_outcome` drops the history it is handed.

**The decisions, each with what was rejected:**

- **Identity is an Ed25519 key the client holds; a name is a label.** The rating id is `key:<base32>`. The secret has its own 0600 file, never `settings.json` (the file people paste into bug reports). Rejected: accounts — a user table, a reset flow and a secret the *server* must protect, for a hobby server. A new pure crate `netrunner_identity` carries it; `netrunner_core` keeps its three dependencies, and `deny.toml` needs no edit (`ed25519-dalek` is BSD-3-Clause, already allowed).
- **Proved by a challenge that names the server.** `Identify` → `Challenge { nonce, server_key }` → `Prove`, signed over `"netrunner-auth-v1" ‖ server_key ‖ nonce`: the server's own key in the signed bytes is what stops a hostile server relaying an honest one's challenge to log in there as its visitor. An unidentified `Connect` still plays, unrated. The handshake protects the key, not the session: a public rating server sits behind TLS, as a deployment requirement and not daemon code.
- **Seat commitments and a server receipt, not a signature per action.** Each player signs once at `MatchJoined` (match, side, both keys, deck hash); the server signs the finished record's hash with the result and sends both players that receipt in a new `ServerMessage::Rated` — which is also Phase 3 §2's "not built: telling the remote client its new rating". Statements are signed as bytes, never as re-serialized JSON. Rejected *for now*: a per-action hash chain, which buys verification by someone who does not trust the server (federation, portable ratings) at a signature per `SubmitAction`; the record's footer reserves the field.
- **The results log is the truth and `ratings.json` is a cache.** Append-only receipts under `--data-dir`; folding them through `RatingBook::record` in order rebuilds the book exactly, so a corrupt book, a Glicko parameter change or voiding a cheater's games is a rebuild. Rejected for now: SQLite — nothing yet asks what a fold over a log cannot answer.
- **What is never rated:** any game with a bot in it (Phase 3 §2), and a game hosted in-process from the menu — the host's process holds the seed. Phase 6 §3's "Open: hosted games are unrated" closes as *by design*. Online, `Rewind::Free` is the only take-back a rated game offers; `Rewind::Undo` needs the other seat's consent — which is why the session's line and the engine's two classifiers were kept when local play stopped charging for it.
- **The trust boundary, stated:** a rating is a claim by one server's operator, who can see every seed. Keys are free, so a new key is provisional. Smurfing and win-trading are moderation, which the rebuildable log makes possible and cryptography does not solve.

**Stages, each its own branch and each useful without the next:** (a) the server keeps match records — no protocol change, and the server half of Phase 7 §8 item 15; (b) `netrunner_identity`, the client's key file, the handshake, ratings keyed by key; (c) seat commitments, receipts, `Rated`, `results.jsonl`, `--rebuild-ratings`; (d) client surfaces — the game-over panel and "your standing at `<server>`" on Profile, fetched and never stored as truth; (e) the free take-back online.

**Open:** `netrunner_client` does not depend on `netrunner_server`, so the desktop's online play (Phase 7 §7) needs `ClientMessage`/`ServerMessage` somewhere lighter — most likely a `netrunner_protocol` crate; decide at stage (b), when the second consumer exists. Key rotation (a successor statement signed by the old key) is recorded and not designed.

## 6. A host reachable from outside — OPEN (25 September 2026); item 1 built

Asked for as: a person hosts on their home network and friends outside it join, with no firewall rules. Three items, in order, each its own branch.

**What stood in the way.** Host a game bound `0.0.0.0` or `127.0.0.1`, IPv4 only. The address it shared came from an IPv4-only routing trick. `netrunner_server --host ::` built `::::8080`, which does not parse. `normalize_address` read the last group of a bare IPv6 address as a port. Nothing asked the router to open anything. The server itself was never the obstacle: it is a plain WebSocket listener and has served the whole of §1–§3 over one.

1. **IPv6, one dual-stack socket, and the router asked to open the port** (`feat/host-reachable-from-outside`, built):
   - `netrunner_client::hosting` binds `[::]` with `IPV6_V6ONLY` explicitly off, falling back to `0.0.0.0`. The option is set explicitly because Windows defaults it on.
   - It lists the addresses to give out, each with who can use them: the LAN IPv4, then a global-unicast IPv6.
   - For a third choice, "anyone on the internet", it asks the router for a TCP mapping over UPnP-IGD, NAT-PMP and PCP (`portmapper`, n0's).
   - The server gains `Server::from_listener` and no dependency; the daemon's `--host` brackets an IPv6 address.
   - **A mapping is reported as reachable only on a public address:** one on `100.64.0.0/10` or a private range is the router behind the provider's NAT.
   - **Every failure names the manual forward and Tailscale.** The forward is left out when the provider's NAT makes it useless.
   - `portmapper` added 47 crates to the workspace lock, all under licences `deny.toml` already allows. The alternative was `igd-next` with `crab_nat`: two crates for three protocols, and renewal to write.
   - Not tested against a router here: the TUI's handling of every answer is tested through a fake `PortMapper`. The real round trip is the manual check in the PR.
2. **A sans-IO client connection in `netrunner_client`.** The handshake, queueing, resume and grace are a state machine (input bytes, output bytes, timeouts) that a client drives, rather than tokio tasks and a `Reconnector` that blocks. This is the pattern Firezone describes ([sans-IO](https://www.firezone.dev/blog/sans-io)). It makes reconnect and lobby tests deterministic without sockets, lets the terminal and the desktop share one connection (Bevy cannot block, AGENTS.md §5), and makes a second transport a transport change. It is also what Phase 7 §7, the desktop's online screen, stands on, and it settles §5's open `netrunner_protocol` question in passing.
3. **A peer-to-peer transport: join by ticket, not by address.** A QUIC transport with hole punching and a relay as fallback (iroh is the candidate; its peer identity is an Ed25519 key, which is §5's player identity). This is what reaches a host behind carrier-grade NAT with nothing installed, and it encrypts what WebSocket sends in the clear today. Its own design first: the relays are a service somebody runs.

**Rejected, with the reasons:**
- **STUN alone.** It tells a machine its public address and nothing more. Hole punching also needs somewhere for the two sides to swap addresses, and a TURN relay for the NATs that defeat it (symmetric, carrier-grade). It is dependable only over UDP, while the game runs over TCP. That is item 3's shape, not a step on its own.
- **Raw WireGuard built into the app.** It is a tunnel, and someone must still be reachable and keys still exchanged: that is rebuilding Tailscale.
- **Tailscale or ZeroTier used as they are** need no code and work through every NAT, so they are the documented fallback (`docs/playing-online.md`), not a feature.
